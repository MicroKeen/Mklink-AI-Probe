## 旧安装包对照

合成两段共 137161 条 JSONL 采样，调用已安装的 `mklink-sidecar.exe` 的 Excel 导出入口。对照组校验了 XLSX 的 ZIP 完整性，数据页有 137161 条采样和一行表头。第二组在另一进程打开 `.mklink-xlsx-*/tmp*` 文件并在导出期间保持打开，两段均已处理，随后导出报 WinError 32。另在源码导出的打包阶段将一个临时文件设为只读，Windows 返回 WinError 5。三种情形的原始 JSONL 校验值均保持一致。

导出器在记录目录中独占创建同名 XLSX，并在同目录创建工作子目录。XlsxWriter 写入、打包和移除临时文件。此阶段的异常会令本次导出失败，导出器尝试移除自己刚创建的工作簿。后台只启动一次转换，GUI 在失败后禁用按钮。截图的临时文件路径与受控占用结果一致。现有客户信息无法判定占用进程，也不足以将口述的 WinError 5 定位到某个具体文件操作。

## 桌面和 Web 使用同一符号文件

对同一测试后台调用配置页与仪表盘使用的接口：

1. 通过 `/api/device/parse-axf` 加载原始绝对路径，通过 SuperWatch 添加 `_thread.init_tick` 并设置别名及颜色。
2. 用 `/api/files/symbol` 上传相同 AXF，确认内容字节一致。解析返回的上传路径后，变量及显示设置均为空。桌面端使用 `controller.axf.superwatch.json`，上传副本使用工程内 `.mklink/uploads/file-sources/<SHA256>.axf.superwatch.json`。
3. 再解析原始绝对路径，变量、别名和颜色恢复，原配置字节未变。同一工程重复上传相同内容会复用上传副本。浏览器连接远端时，手动填写的路径须能从后台主机访问。

旧版复现脚本位于构建根目录下的 `reports/superwatch-export-profile-20261124/`。同目录上一级的 `run-20261124-150505-83308131.log` 为两个错误码和行数对照，`run-20261124-150613-7b590a73.log` 为安装版对照，`run-20261124-150523-090bc89a.log` 为真实 AXF 的接口验证。


## 修复与实板验收

- Windows 转换器在同一用户工程内写工作簿，使用操作系统管理的临时句柄。转换失败后可以重试。已有同名输出、原始分段和此前完成的分段分别保留。
- 桌面记录打开过的 AXF/ELF。浏览器选择文件时，后台核对文件名、长度和完整 SHA-256，再复用原工程的配置。两个已知工程使用同名同内容文件时，界面列出候选路径供选择。
- SuperWatch 保存显示设置、CLI 接入已有采集会等待短暂的设备读操作；切换目标、独占任务、配置版本冲突仍有独立检查。
- SystemView 默认保存到当前用户工程的 `.mklink/logs/systemview`。桌面默认工作区缺少原始符号路径时，可通过“日志位置”指定工程。摘要失败后可以单独重新生成，桌面与浏览器均支持导出已保存的记录。JSONL 末行和摘要的 events 按实际落盘行数计，stream_events 单列整个采集会话的累计数。任务耗时与离线分析使用相同的调度和中断规则。
- 目标内存读失败时显示操作、地址、字节数、设备回复及建议。同一 JTAG IDCODE 可由多个型号使用，诊断时应对照板上程序和对应 ELF。状态 5 表示目标访问失败。`0x16` 是块读取命令。单凭这些信息无法区分供电、调试模块、地址或缓存问题。
