# 0.4.3 IAR 退出后吞吐恢复与四调试器共存

2026-11-06。上位机保持 `codex/v0.4.3-fixes` / `92ca42e0` 的心跳和录制实现。
本轮产品修复在 V3 固件的 `codex/v3-iar-context`，基于 `05f1fb2`；未修改目标程序、
上位机产品代码或正式固件目录。未合并、发布或构建覆盖上位机安装包。

本报告接续 [MUX 心跳与录制验收](v043-mux-heartbeat-recording.md)。范围是已复现的
IAR 正常退出后吞吐不能自行恢复。客户旧 V3 固件的双端卡死在当前版本未复现，
不将本次结果表述为该故障已经修复。

后续普通 V4 的原 E/r4 对照及四调试器复验见 [V4 验收](v043-v4-iar-exit-context.md)。

## 原因与实现边界

本机 IAR 9.70.1 的 CSpyBat 正常退出和真实 GUI Stop Debugging 均已抓取完整
WinUSB 提交及完成数据：分别 4665、10747 对 OUT/IN，零完成缺失、失败或缓冲复用漏记。
两条路径都有成功的 Connect 和 HostStatus CONNECTED=true，但均未发送 Disconnect、
CONNECTED=false 或 7E/7F 批量命令，最后成功请求后关闭句柄。追踪只观察，不改写请求/回复；
追踪进程已退出，GUI 重启后才做性能与兼容验证。

因此不能用无 DAP 请求、CPU 状态或主机句柄关闭推测调试会话已经结束。
原 L 固件保留逻辑 active，连续流每批反复保存、恢复 AP 上下文及软件时钟，导致持续开销。

候选保留逻辑调试所有权与一次快照，仅让连续 MUX 流跨有界采样批次保留该快照。
每批仍释放互斥锁，新 DAP 请求保留优先级；获准执行的 DAP 或普通 MUX 控制访问前先恢复
SELECT/CSW/TAR、DAP 软件状态和时钟。普通控制即时借还，拒绝的 legacy 轮询不破坏健康快照。
恢复失败阻止后续访问，流错误触发恢复，USB 代次变化使旧快照失效。

这修复的是残留状态导致的吞吐开销，**没有通过超时清 active，也没有声称识别了 IAR 退出**。
同一路径供 Keil、pyOCD 和 OpenOCD 使用，故分别验证它们与 RTT/SuperWatch 的共存。

IAR 并行、正常退出、后续正常调试关闭，各阶段三次。

正常退出后 RTT 中位提升 18.29%，Watch 提升 17.48%，自动回到相邻无 IDE 水平，
没有通过额外 DAP Disconnect、重新连接或重启恢复。无 IDE RTT 中位变化 -0.033%，

此混合负载对照不替换其他映像/负载下独立 RAM 约 26.2 万/s 或独立 RTT 约 854 KiB/s 基线。

500 MSa/s、2 ms 的退出波形配对中，原 L 有五组完整借上下文序列和五次原 CSW 恢复，
候选均为零。两组主要连续 SWCLK 周期均 32/34 ns，约 30 MHz。
有效事务解码用于正向序列证据，不能当作完整错误计数，也不外推保存窗口之外的行为。

四类调试器分别和 RTT/SuperWatch 并行，不是同时启动四个调试器争用 CMSIS-DAP。

各退出后 Watch 共同窗口约 11.7 万 samples/s。暂停时目标停止产生新 RTT 是预期行为，

既有的部分变量位置提示，本测试不声称两套 IDE 的全部符号表达能力等价。
