# V3 / STM32F103RET6 regression — 2026-09-18

Development qualification only; no firmware or application release. Tests use
V3.5.0 development firmware and the STM32F103RET6 RT-Thread test application.
The final UF2 SHA-256 is
`404320065c05a324a46044c78ce6bcd1bb71e7fe84e16d3b9c25da1cb138d3c7`.
Its payload matches the 383302-byte application binary.

## Sampling

Each speed ran a 30-second fixed 4-byte RAM capture, a 10-second 4 KiB capture,
and a 10-second 15-region capture. Payload, CRC, status flags and monotonic
timestamps passed. Timestamp rates include gaps between batches; host rates
use the steady receive interval. These are different measurements.

| Requested SWD | 4-byte timestamp rate (Sa/s) | Host steady rate (Sa/s) | 4 KiB (KiB/s) | 15-region vectors/s | Largest 4-byte gap (µs) |
| --- | ---: | ---: | ---: | ---: | ---: |
| 10 MHz | 116135 | 117132 | 564.71 | 2863.56 | 285 |
| 20 MHz | 184739 | 186310 | 856.57 | 4226.32 | 216 |
| 30 MHz | 182522 | 184061 | 1003.38 | 5037.51 | 272 |

30 MHz improves block and multi-region throughput here; it does not improve
single-word sustained rate over 20 MHz. Earlier four-profile mixed-width and
unaligned-address tests passed, including 265304 atomic-word frames with six
byte/halfword interpretations each. Arbitrary packed odd-address halfwords
are not guaranteed atomic. The customer's original application was unavailable.

## GUI and AI shared stream

The GUI owns the probe; AI observes its WebSocket stream. With compression
enabled, a 20 MHz run overflowed the broadcast queue and also recorded three
CRC errors; this does not establish compression as the cause of the CRC errors.
Disabling WebSocket per-message deflate avoids repeatedly compressing compact
binary sample records for each client. Fresh real Chrome runs passed:

| Speed | Duration | AI received samples | Timestamp rate | Host rate | Sequence gaps / CRC errors / dropped broadcast batches |
| --- | ---: | ---: | ---: | ---: | --- |
| 20 MHz | 20 s | 2818753 | 158273 Sa/s | 140868 Sa/s | 0 / 0 / 0 |
| 30 MHz | 30 s | 4395072 | 172980 Sa/s | 146359 Sa/s | 0 / 0 / 0 |

Queue high-water mark was five batches with multiple consumers. Real Chrome
waveforms were inspected and captured. These finite runs are not multi-hour
or cross-platform certification.

## Other regressions and fixes

- Firmware RTT start ordering now queues the command response before streaming.
  Previously an 8191-byte upload could lose its first chunk. Three speeds,
  ten 8191-byte patterns each, passed after the fix (245730 bytes).
- RTT downlink queues data against the target ring's available capacity;
  four speeds × 100 × 256-byte echo patterns passed (102400 bytes). Stopping
  with a full target ring completed in approximately 302 ms at each high speed.
- RTT/SystemView exact-address search supports both zero and the host's legacy
  four-byte search argument. Real MCP dynamic RTT and static SystemView passed.
- UART at 115200 passed 300 exact 1324-byte shell responses (397200 bytes).
- CLI `--frames` now stops at the requested complete sample rather than consuming
  the remaining samples in a USB read. Three speeds each saved exactly 10000
  four-byte samples. Regression tests cover ordinary and split block frames.
- Targeted Python suites: 42 dump-session tests and 141 online-probe/Web-entry
  tests passed. No full release suite or installer qualification was performed.

## Clock calibration

LA5032 at 500 MHz measured valid SWD read-data periods. GUI configuration
10/20/30 MHz measured approximately 10.084/20.163/30.247 MHz. Online and offline
flash read phases similarly measured approximately 4.08/10.08/20.17/30.24 MHz
for the four profiles. Keil requests 1/2/5/10 MHz measured
1.0003/2.0063/4.9686/10.0853 MHz, with successful verify in each case.

## Repeated flash investigation

Offline: 10 MHz with chip erase (3 runs), 30 MHz normal (10 runs), and 30 MHz
with chip erase (3 runs) passed. Every run independently read back all 135320
image bytes and checked that the RT-Thread tick advanced. The boot prefix was
preserved in the test image so chip erase did not remove application startup.

Online 30 MHz under-reset: the third run reproduced an erase-stage failure,
`register xpsr not available in this CPU`. The old matching image remained
intact and running, which does not prove that this failed run programmed it.
Investigation is ongoing; online 30 MHz is not qualified by these results.
