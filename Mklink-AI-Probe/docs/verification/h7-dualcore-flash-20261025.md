# STM32H7 双核 Pack 烧录候选修复

## 状态与范围

分支 `codex/h7-dualcore-flash`，实现提交 `e7f357bd`，审查补强提交
`7c3b2f56`；PR #54 为草稿。仅交付 Windows 测试包，版本号仍为 0.3.6，
不修改正式发布渠道、更新索引或下载器固件。没有 H745/H747/H755/H757
实物，本报告不能作为客户故障已闭环的证据。

## 原因与处理

Keil.STM32H7xx_DFP 4.1.3 的同范围算法分别指定 CM7 和 CM4。
pyOCD 0.44 的 `_extract_algos` 按 Flash 起始地址和长度合并，后面的 CM4
覆盖 CM7，使 CM7 执行算法时误用 `0x10000000` RAM。客户 CM4 HEX 位于
`0x08100000`，发生初始化超时，与这个软件缺陷吻合，但尚未排除其他现场原因。

针对 STM32H745/H747/H755/H757，在有损合并前选择 CM7/通用算法，保留
供应商 RAM 地址、大小及继承关系；不改 Pack 文件、不全局替换 RAM 常量。
算法目录、字节提取、在线内存预览、脱机 Pack 列表及在线 Session 都安装同一兼容层。
依赖限制仍是 `pyocd>=0.44,<0.45`；升级该依赖前须重验内部解析接口。

在线操作绑定实际 CM7 名称与 AP0，不能只按核心枚举顺序选择。擦写前确认
CM4/AP3 可访问并停止两核；无法确认时拒绝擦写。只读连接不额外暂停 CM4。
失败或未执行复位的烧录不在断开时自动恢复核心，避免运行 RAM 算法或旧 PC。
显式复位运行使用系统/硬件复位，检查 CM7 和 CM4 状态后才允许正常断开恢复。
核心单独复位不适用于此流程，在擦写前拒绝。电源循环仍须原有电压授权。

脱机入口修改仅统一 Pack 元数据解释，不代表下载器固件已具备双核停止/恢复流程，
本测试交付以在线烧录为验收范围。

## 客户试测

1. 保存当前工作，安装带 `h7-dualcore` 与源提交号的测试安装包；界面版本仍显示
   0.3.6，不能仅用版本号判断是否安装本候选。
2. 先关闭同一下载器上的 Keil 等调试会话，选择准确 MCU 型号及
   `Keil.STM32H7xx_DFP@4.1.3`，内部 Flash 算法 `STM32H7x_2048.FLM`。
3. 加载原 CM4 HEX，确认地址来自 HEX（预期 `0x08100000`），按文件覆盖扇区
   擦写并启用回读校验；不要为本测试执行整片擦除、解锁保护或修改选项字节。
4. 默认系统复位；连接 NRST 时可以选择硬件复位。不要选择仅核心复位。
5. 分别检查下载、回读以及复位后 CM7/CM4 应用行为。若只执行烧录而未选择复位，
   核心会保持暂停，需要明确执行系统/硬件复位后运行。
6. 失败时先导出后台管理页面的诊断包，记录芯片完整型号、下载器型号/固件版本、
   Pack、NRST 接线及所选复位方式，不反复尝试未知结果的擦写操作。

仍待真机：四系列全部硬件组合、第二核被禁用/休眠/不可访问时的提示与行为、
不同 boot/复位配置、双核重启及客户原 HEX 的完整回读。
