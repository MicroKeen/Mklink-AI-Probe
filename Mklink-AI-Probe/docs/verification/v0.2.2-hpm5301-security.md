## 发现及修复

### 受保护内存被错误报告为全零

DEBUG_DISABLE 生效后，探针仍可读到 IDCODE，但旧 SBA 路径在 DMI 返回全零时
把 SBCS 当成“无错误”，继而向主机返回四个零字节。UART 同时回报真实的
安全字为 0x100A0001，因此这是无效读，不是数据本身为零。

固件修复：普通 SBA 读写（包括流读取的回退路径）开始前检查 SBCS 的版本、
地址宽度与 32 位访问能力。不可用时直接失败，不再产生虚构的内存内容。
已编译、升级 HPMLink.uf2，并在 DEBUG 已禁用的芯片上复测。

上位机修复：`Device.read_memory` 要求返回字节数等于请求长度；空响应和部分
响应均抛出明确异常，不再向 API 使用者返回空数据作为成功。
修复后的真机结果为：`returned 0 bytes, expected 4; target debug access may be disabled or unavailable`。
正常未锁目标的固件读写回归已在第二颗芯片完成：38,132 字节 ROM 下载、完整校验及递增 tick 通过。此前 52 项相关 Python 测试通过。

### 通用 halt/run 不作为本次 HPM 调试判据

审查发现主机通用 halt/run 路径采用 Cortex-M 寄存器模型，探针通用 CPU 命令在
本次 HPM 未锁状态也返回 -1。本报告没有把这些返回值当作 DEBUG_DISABLE 的证据。
禁用前的正常下载和内存读、禁用后的 SBA 拒绝、UART 独立读回及持续运行分别记录。
HPM 通用 CPU 控制接口的一致性另需修复验证。
