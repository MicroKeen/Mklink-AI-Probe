# 连接后固件升级提醒

日期：2026-11-13。开发基线 `59de468b`，实现 `cb54b361`，
分支 `codex/v0.5.0-fixes`。这是源码及生产 Web 验证，不是安装或正式发布。

## 行为

- 复用连接握手已有的 `cmd.get_version()` 响应，不增加串口命令、USB 枚举或目标访问。
  首次读取连接状态后延迟 3 秒，在后台线程查询既有云端通道，不等待网络再返回连接或状态。
- 仅比较相同产品、相同硬件代际的语义版本。无产品标识默认 MicroLink；显式
  `PROBE_PRODUCT=HPMLINK` 选择 HPMLink。V2 查询独立的 V2 索引，不推荐 UF2。
- 云端更高时返回 `firmware_update.status=available`；相同或当前更高时不弹窗。
  自动检查不把离线的内置索引称为云端结果；显式手动升级保留原有回退机制。
- 用户要求无法识别的老格式也直接提醒：已连接但版本/产品信息不能解析时返回
  `unrecognized`，提示升级、进入固件页，不编造版本、不自动选择未知型号的镜像。
- Web 提供“稍后”和“前往升级”。后者仅打开配置 → 固件升级，不停止采集或刷写。
  同一窗口会话、下载器及版本组合去重，重新加载页面也保留；版本变化或更换下载器可再次提醒。
- 网络失败静默，失败结果缓存 15 分钟，成功结果缓存 6 小时。状态读取不等待后台任务，
  同通道合并在途检查；切换设备时用当前缓存身份重新比较，不复用上个设备的结论。
- Web、CLI/SDK、MCP 共用 `device_status.firmware_update`。Skill 参考与 MCP 说明同步。
  远程 Web 保留现场用户升级的能力提示；固件升级入口仍在本地。
- 保留操作前的能力协商、型号边界和显式升级确认。用户可以暂不升级，版本比较不能代替能力检查。

## 版本格式核对与实机发现

核对 V2、V3、V4 固件的 `cmd_get_version` 与 `VERSION` 定义，未修改固件源码：

| 来源 | 返回形式 | 处理 |
|---|---|---|
| V2 | 说明链接、当前 `V2.x.y`、可能包含多个历史版本、能力行 | 保留响应顺序，读取第一个版本行 |
| V3 | 时序/UART 能力行、当前 `V3.x.y`、说明链接及其他能力行 | 允许版本前后存在其他内容 |
| MicroLink V4 | UART/RS485/时钟能力行、当前 `V4.x.y`、其他能力行 | 缺产品标识按 MicroLink |
| HPMLink V4 | 同 V4，额外 `PROBE_PRODUCT=HPMLINK` | 独立产品匹配 |

V2 的处理函数位于 `external/pikapython/pikascript-lib/cmd/cmd.c`，V3/V4 为
同目录的 `py_cmd.c`；版本文本位于各应用的 `src/flash_fatfs.c`。
本次看到 V3 源码标记 V3.7.0、V4 标记 V4.7.4，这只是本地开发源码的观测，
不意味着它们已经发布至正式云端。

实际接入的一只下载器为 **V2.9.4**，不是此前的 V4。初版检查把它判为未知，
原因是能力集合同时包含 V2.9.4、V2.9.3、V2.9.2，集合丢失了顺序。
修正为保存握手原文、使用现有版本解析器的首个版本行；重连清空缓存。
既有能力提示也改为使用这个当前版本，避免同一问题使能力清单失效。
诊断时额外显式读取过一次版本；产品的自动检查没有新增查询。

修正后真实共享后台首次连接返回 `checking`，用时约 1.087 秒（包含后台启动和附着）。
随后云端 V2 通道返回 V2.9.3，结果为 `current`，没有建议降级。
等待期间 31 次状态请求 P95 约 5.798 ms、最大 34.257 ms。
这些是一次短测的观测，不能代替连接性能 A/B 或采样吞吐验收。
正常分离后后台退出并释放下载器；未刷固件、未修改电源或目标程序，未启动采集。
